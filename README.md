# Azure Management VM (Jumpbox) - Standalone Project

Terraform project that deploys a fully network-isolated Linux VM for ad-hoc scripts, troubleshooting, and verification tasks. This project is **independent** from the network project (`azure-virtual-network`) - it attaches into an existing subnet by ID, but never creates, modifies, or destroys the VNet, subnets, NSGs, or any other networking resource.

## Why this design

This VM has no public IP and no inbound network exposure of any kind. It was deliberately built this way instead of using a traditional SSH bastion or the managed Azure Bastion service, trading interactive convenience for a minimal attack surface and zero ongoing service cost.

Access works through two Azure control-plane mechanisms instead of network connectivity:

| Mechanism | Use case | Requires network path to the VM? |
|---|---|---|
| `az vm run-command` | One-off commands, scripts, automation | No - goes through Azure Resource Manager |
| Azure Serial Console | Interactive shell session, boot diagnostics | No - goes through the Azure control plane |

Neither mechanism touches the VNet's data plane. The VM's NSG (inherited from the subnet it's deployed into) can keep denying all inbound traffic with zero exceptions.

## Architecture

```
azure-virtual-network/  (separate project, deployed first)
└── snet-app  (existing subnet, referenced by ID; regional, spans all AZs)
        │
        │ var.app_subnet_id (passed explicitly, no remote state read)
        ▼
azure-jumpbox-server/  (this project)
├── nic-mgmt-jumpbox    (private IP only, no public IP)
└── vm-mgmt-jumpbox     (Ubuntu 22.04 LTS)
```

## What this deploys

| Resource | Notes |
|---|---|
| Network Interface | `nic-mgmt-jumpbox`, private IP only, attached to the existing subnet passed via `app_subnet_id` |
| Linux Virtual Machine | `vm-mgmt-jumpbox`, Ubuntu 22.04 LTS, no public IP, `mysql-client` + `postgresql-client` + `kubectl` installed via cloud-init on first boot |
| SSH key pair | Generated by Terraform (`tls_private_key`), satisfies Azure's API requirement for VM creation, never written to disk, never used for actual access |

This project does **not** create a resource group, VNet, subnet, or NSG - those belong to the network project and are referenced as a data source (`data.azurerm_resource_group.existing`).

## Network placement

Deployed into the App subnet (`snet-app`) of the network project - private (NSG-Private denies all inbound except from the Public/AppGW subnets; run-command and Serial Console don't need inbound access, they go over the Azure control plane) with outbound Internet via the shared NAT Gateway (needed for cloud-init to fetch the `mysql-client`/`postgresql-client` packages on first boot). NSG-Data already allows inbound from the App subnet's CIDR to the Data subnet on `3306`/`5432` (among other DB ports), so this VM has a ready-made path to reach a MySQL or Postgres instance whose Private Endpoint sits in the Data subnet (e.g. `azure-mysql-database`) - no NSG changes needed on either side.

## Using this as a database bastion

1. Connect via Serial Console (see below) - interactive, works today.
2. From the shell: `mysql -h <db-private-ip-or-fqdn> -u <user> -p` or `psql -h <db-private-ip-or-fqdn> -U <user> -d <database>`.

Serial Console is a real terminal but not SSH - no scrollback search, no local copy-paste shortcuts, and some TUI-heavy tools feel clunkier than over SSH. It's the tradeoff for zero inbound exposure; fine for occasional `psql`/`mysql` sessions, more friction for long interactive work.

## Using this as an AKS bastion

`kubectl` (via snap) is installed on first boot, ready for whenever the `azure-aks-cluster` project exists in this VNet. Two things still need to happen at that point, neither of which is set up yet:

- **Credentials**: get a `kubeconfig` onto this VM (e.g. `az aks get-credentials`, which needs the Azure CLI - not installed here yet since it isn't available as a snap package; the officially documented apt-repo install is the way to add it if/when needed) or copy one over via `az vm run-command`.
- **Network path**: whether this VM can reach the cluster's API server depends on decisions the AKS project hasn't made yet (private vs. public API server, authorized IP ranges, NSG rules). Revisit this once that project is built - nothing to guess at from here.

## Remote state

State lives in the shared Azure Blob Storage backend provisioned by `azure-tfstate-bootstrap` (see `backend.tf`), under the key `jumpbox/terraform.tfstate` - not local, not committed.

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.5.0
- [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli), logged in via `az login`
- The network project (`azure-virtual-network`) already deployed - you need its `resource_group_name` and `app_subnet_id` outputs
- The `azure-tfstate-bootstrap` project applied first (this project's backend depends on the storage account/container it creates)

## Getting the required inputs from the network project

From the `azure-virtual-network` directory:

```bash
terraform output -raw resource_group_name
terraform output -raw app_subnet_id
```

## Configuration

`subscription_id` has no default (kept out of the repo on purpose) - export it as `TF_VAR_subscription_id` or pass `-var subscription_id=<id>`.

Create a `terraform.tfvars` file in this directory (already excluded by `.gitignore`):

```hcl
resource_group_name = "rg-network"
app_subnet_id        = "/subscriptions/<sub-id>/resourceGroups/rg-network/providers/Microsoft.Network/virtualNetworks/vnet-ha/subnets/snet-app"
```

| Variable | Default | Description |
|---|---|---|
| `subscription_id` | — | Azure subscription ID (required explicitly by azurerm >= 4.0) |
| `resource_group_name` | `rg-network` | Name of the EXISTING resource group from the network project |
| `location` | `centralus` | Must match the existing VNet's region |
| `app_subnet_id` | *(required, no default)* | Full resource ID of the existing App subnet to deploy into |
| `mgmt_vm_size` | `Standard_D2s_v3` | VM size |
| `mgmt_admin_username` | `azureuser` | Local admin username on the VM |
| `mgmt_zone` | `1` | Availability zone to pin the VM to (the subnet itself already spans all AZs) |

## Deploy

```bash
az login
export TF_VAR_subscription_id="<your-subscription-id>"
terraform init
terraform plan
terraform apply
```

This creates only the NIC and VM (plus the disposable SSH key) - it never touches the network project's resources.

## Accessing the VM

Two ways in, neither needs a network path to the VM (see "Why this design" above).

### One-off commands

```bash
az vm run-command invoke \
  --resource-group rg-network \
  --name vm-mgmt-jumpbox \
  --command-id RunShellScript \
  --scripts "hostname && uptime"
```

No setup needed. Each call is a single round trip - not an interactive session.

### Interactive shell via Serial Console

Serial Console logs into the VM's local OS account (`azureuser`) with a password - it's not SSH, so the disposable SSH key Terraform generates doesn't apply here, and `disable_password_authentication` on the VM resource (which blocks SSH password auth) has no effect on it either.

**1. Set/rotate the password.** Paste these lines exactly as-is, as one block, into your own terminal (never share the output with anyone, including pasting it into a chat):

```bash
JUMPBOX_PW=$(openssl rand -base64 24 | tr -dc 'A-Za-z0-9' | head -c 20)

az vm run-command invoke \
  --resource-group rg-network \
  --name vm-mgmt-jumpbox \
  --command-id RunShellScript \
  --scripts "echo 'azureuser:${JUMPBOX_PW}' | chpasswd"

echo "$JUMPBOX_PW" > ~/jumpbox-password.txt
echo "Password guardada en ~/jumpbox-password.txt - copiala a tu gestor de contraseñas y después borrá el archivo"
unset JUMPBOX_PW
```

Then: `cat ~/jumpbox-password.txt`, save it in a password manager, and `rm ~/jumpbox-password.txt`.

**2. Connect** - Portal or CLI, pick one:

| Where | Steps |
|---|---|
| Azure Portal | Open `vm-mgmt-jumpbox` → left menu → **Connect** → **Serial console** tab |
| CLI | `az extension add --name serial-console` (once), then `az serial-console connect --resource-group rg-network --name vm-mgmt-jumpbox` |

At the `login:` prompt: user `azureuser`, password from the file above. To exit: close the Portal tab, or `Ctrl+]` then `q` on the CLI.

### Why not plain SSH?

No public IP, and the subnet's NSG denies all inbound traffic - there is no network path for SSH to reach this VM. The two mechanisms above are the only supported access methods, by design.

## Sharing this project with others

1. They need the network project's outputs (`resource_group_name`, `app_subnet_id`) - get these from whoever manages `azure-virtual-network`, or by running `terraform output` there directly since state is shared remotely.
2. They create their own `terraform.tfvars` with those values - never commit this file (already covered by `.gitignore`).
3. Each operator sets their own Serial Console password (see above) rather than reusing someone else's.
4. Serial Console access also requires the `Virtual Machine Contributor` (or higher) Azure RBAC role on this VM, on top of the OS login.

## Destroying

```bash
terraform destroy
```

This only removes the NIC and VM created by this project - the VNet, subnets, NSGs, and all other network resources remain untouched.

## Security notes

- No public IP, no open inbound ports - the smallest possible network attack surface for a VM that still needs management access.
- The SSH key pair generated by this project is never used and never written to disk - it exists only to satisfy Azure's VM creation API. It does live inside the Terraform state file, which is why state is kept in the remote backend (encrypted at rest, access gated by Azure RBAC) rather than local disk or version control.
- The Serial Console password is set out-of-band via `run-command`, not stored in Terraform state or any `.tf` file - rotate it periodically using the same commands (see "Accessing the VM"). The password only ever touches your own terminal and a local temp file you delete right after - never paste it anywhere else.
- Outbound internet access (e.g. for `apt-get update`) flows through the network project's shared NAT Gateway, associated with this subnet.
- `subscription_id` has no hardcoded default - see Configuration above.
